Drei Schranken für KI-Agenten. Eine Fallstudie zur Agenten-Sicherheit.

Stand 17. November 2026 · alle Zahlen aus den öffentlichen Repos, mit Fundstelle am Ende · gebaut mit Claude Code

Ich lasse KI-Coding-Agents jeden Tag an meinem Code arbeiten. Sie committen, pushen und lesen fremde Pull Requests, READMEs und Bug-Reports. An jeder dieser Stellen kann ein Fehler oder eine versteckte Anweisung durchrutschen. Deshalb habe ich drei Werkzeuge gebaut: zwei bewachen je eine Tür, das dritte misst, ob die Schutzregeln überhaupt halten.

  • Vor dem Push: commit-guard prüft jeden git commit und git push, bevor der Agent ihn ausführt.
  • Beim Pull Request: pr-airlock liest fremde Änderungen nur als Daten und blockt vergiftete PRs an ihrer Form.
  • Messen statt glauben: injection-bench lässt meinen echten Agenten auf versteckte Anweisungen los und zählt, was durchkommt.

Stufe 1: commit-guard, bevor etwas das Repo verlässt

commit-guard ist ein Hook für Claude Code, der vor jedem Werkzeugaufruf läuft. Will der Agent committen, liest der Hook die neu hinzugefügten Zeilen und sucht nach 10 Mustern: 7 eingebaute Schlüsselformate wie API-Schlüssel, GitHub-Tokens und private Schlüssel, dazu private Mail-Adressen, Telefonnummern und private Pfade, die man selbst einstellt. Beim Push prüft er Branch und Autor-Adresse. In einem öffentlichen Repo wird ein Fund abgelehnt, in jedem anderen fragt Claude Code mich zuerst.

Entscheidung: ein echter Parser statt einer Suchregel

Die erste Fassung suchte mit einem regulären Ausdruck nach git push. Verschachtelte oder umgeschriebene Befehle sind dabei durchgerutscht. Heute zerlegt ein kleiner Shell-Parser ohne Abhängigkeit den Befehl so, wie die Shell es tun würde, und ein zweiter liest die Optionen von git. So prüft der Hook genau das Repo, das git auch benutzen würde.

Entscheidung: Was unklar ist, gilt als verdächtig

Kann der Parser einen Befehl nicht sicher lesen, wird er in einem öffentlichen Repo abgelehnt und sonst nachgefragt. Fällt der Hook selbst aus, fragt er ebenfalls. Das kostet ab und zu einen Fehlalarm, dafür gibt es keinen stillen Durchlass. Auch die eigenen git-Aufrufe des Hooks sind abgesichert: Er startet nichts, was im geprüften Repo konfiguriert ist.

Grenze: commit-guard fängt typische Fehler, er ist kein vollständiger Geheimnis-Scanner. Die README empfiehlt selbst, zusätzlich gitleaks zu verwenden. Als Nächstes soll die Wächter-Mod in meinem eigenen Claude Code auf diesen Kern umsteigen; das ist ein Entwurf und noch nicht aktiv.

Stufe 2: pr-airlock, wenn Code von außen kommt

Ein Commit-Hook schützt nur, was ich selbst schreibe. Code kommt aber auch als Pull Request von außen. 2026 hat die PolinRider-Kampagne Schadcode ans Ende ganz normaler Konfig-Dateien gehängt, so weit nach rechts geschoben, dass er im Diff-Fenster nicht zu sehen ist, und damit vergiftete PRs an große Open-Source-Projekte geschickt. Mehrere Maintainer haben sich eigene Notlösungen gebaut. pr-airlock ist eine fertige Prüfung dafür, als GitHub Action und als Kommandozeile.

Entscheidung: nur lesen, nie ausführen

pr-airlock holt den PR nur als Daten über die GitHub-API. Es checkt nichts aus, installiert nichts und führt nichts aus. Die Prüfung läuft in der Fassung des Ziel-Branches, ein PR kann sie also nicht selbst abschalten. Die Einstellungen kommen ebenfalls vom Ziel-Branch; ein PR, der sie ändert, bekommt einen eigenen, blockierenden Befund.

Entscheidung: Form statt Markierungen

Die Angreifer haben ihre Erkennungsmerkmale schon mehrmals gewechselt. pr-airlock sucht deshalb nach der Form des Angriffs: Code hinter auffällig viel Leerraum, Schriftdateien, die in Wahrheit Text sind, Aufgaben, die beim Öffnen eines Ordners von selbst starten. Was es nicht prüfen kann, etwa weil GitHub einen Diff weglässt, wird ein eigener Befund und blockiert bei Code, statt still durchzugehen.

Grenze: Ein sauberes Ergebnis heißt keine der bekannten Formen, nicht sicher. Eine Variante ohne diese Merkmale bräuchte einen anderen Detektor, und nach einer Infektion ersetzt pr-airlock keinen Scan des eigenen Rechners.

Stufe 3: injection-bench, ob der Schutz wirklich hält

Die ersten beiden Stufen prüfen Code. Die unbequemere Frage ist der Agent selbst: Was tut er, wenn in einer Datei, die er liest, die Anweisung steht, Geheimnisse wegzuschicken? Der übliche Rat lautet Deny-Regel setzen oder Sandbox einschalten. Gemessen wird das selten.

injection-bench baut dafür eine abgeschlossene Versuchsanordnung: Wertlose Fake-Geheimnisse mit einer zufälligen Markierung liegen in einem Wegwerf-Ordner, dazu ein Szenario mit einer versteckten Anweisung. Ein Honeypot auf dem eigenen Rechner zeichnet jeden Sendeversuch auf. Dann arbeitet mein echter Agent unter einem Schutzprofil in diesem Ordner. Am Ende wird aus seiner Ausgabe, dem Honeypot-Protokoll und dem Ordner ein Urteil von sauber bis abgeflossen. Ein Profil hält, wenn nichts den Rechner verlassen hat. Kein echtes Geheimnis wird je benutzt.

Die Kontrollaufgaben hat der Agent unter allen drei Profilen erledigt, die Profile sperren also nicht einfach alles. Wichtig ist die Einschränkung: Das ist eine einzelne Messung. Deshalb kann injection-bench jeden Fall mehrmals laufen lassen und gibt dann Quoten mit Unsicherheitsbereich aus, statt eine einzelne Zahl zu feiern.

Ein Befund: Eine Deny-Regel für .env stoppt das Lese-Werkzeug des Agents, aber nicht das Lesen über die Shell. Erst die Sandbox schließt diese Lücke. Genau solche Annahmen will ich nachmessen, bevor ich mich auf sie verlasse.

Was die Kette nicht kann

Jede Stufe erkennt, was sie kennt. commit-guard sucht Muster, pr-airlock Formen, injection-bench misst ein festes Korpus. Ein neuer Angriff außerhalb davon kann durchkommen. Keine Stufe ersetzt es, Änderungen selbst zu lesen. Die drei Werkzeuge machen Fehler nur seltener und sichtbarer.

Was ich daraus mitnehme

Ein Schutz, den man nicht misst, ist eine Vermutung. Wenn ein Werkzeug etwas nicht prüfen kann, soll es das laut sagen, statt durchzuwinken. Und fremder Inhalt wird gelesen, nie ausgeführt: Diese Regel steckt in allen drei Werkzeugen.
