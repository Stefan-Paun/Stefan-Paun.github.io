What tests taught me. Lessons from two projects.

Note · as of 16 November 2026

At first I thought writing tests was a side issue. Then tests did real damage on my machine, and I understood why tests themselves need rules.

  • Data protection: tests must never touch real data. A guard in the code and a check after every run make sure of that.
  • Flaky tests: a test that is sometimes red and sometimes green often points to a real problem.
  • Rule: I don’t push red tests, and I look at the exit code, not just the output.

A test run changed real data

In Jarvis, tests wrote files into the real data folder several times. Once a file the assistant needs every day was even overwritten. The second time, an agent had started the tests through its own script. Real test notifications probably went to my phone as well.

The cause was simple: my guard recognises a test run by its start arguments. A custom script bypassed it. That was my gap, not only the agent’s.

What I do since then

  • A guard module recognises test runs, redirects the data paths and locks the data folder for other users.
  • Tests only run through the normal command. Custom runner scripts are off-limits and written down as a rule in the project instructions.
  • Before every run I create a marker file. Afterwards there must be no newer files in the data folder. If there are, a test is leaking.
  • The notification tool refuses real push messages under tests.
  • New data sources have to be replaced in tests.

Flaky tests are hints

Some tests in Jarvis fail under load or because of the time of day. I used to restart them and carry on. One case turned out to depend on the time. I wrote an issue for it, and the fix came as a PR. Another finding of the nightly test runs was a write that could collide when two processes ran at the same time. I switched it to atomic saving.

Not every flaky test has a cause. Some stay unexplained, and then I write them down as “known flaky” instead of pretending I know. Live tests with a network and tests with real hardware are unreliable by nature.

I don’t push red tests

In Agent-Board I once pushed although two tests were red. I had only searched the output for a keyword and not checked the exit code. Since then I look at the exit code. In Jarvis my guard also asks before a push if the current state has no green test run. Even a green run on the Mac is not always enough: CI tests Windows, and the night cloud doesn’t see some Mac tests.

A test that doesn’t need real data is better

Where I can, I replace real things with fakes. That makes tests faster and safer. It has limits: a fake can drift from reality, and then the test stays green although the feature is broken.

What I take away

More tests don’t automatically mean more safety. What matters more is that I can trust them. That takes a guard against side effects, a close look at flaky tests and a clear rule for when to push.
