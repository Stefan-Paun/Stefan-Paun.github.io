Jarvis: how my voice assistant is built. Flow, decisions, limits.

As of 17 November 2026 · private project, built with Claude Code

Jarvis is my personal voice assistant. I talk to it, it understands me, uses tools and answers with a voice. I built it in Python, together with Claude Code. The code is private. Here I describe how it works.

  • Flow: a key or “Hey Jarvis”, then Whisper, then Claude with tools, then a voice.
  • Stance: personal data is encrypted, tests may never touch it, and I merge myself.
  • Number: over 4,400 automated tests. That is a lot, but no proof that everything is right.

The path of a request

I press a key or say “Hey Jarvis”. Whisper turns my speech into text. The text goes to Claude, and Claude may use tools, for example for weather, timers or music. The answer is spoken out loud. There is also a web interface for the browser and the iPhone.

Claude does not get all tools at once. The most important ones come with a full description, the rest are listed in one line each and loaded when needed. That saves tokens. On top of that there is a fixed budget for the start of every request. If a description gets too long, I shorten it. I don’t raise the limit.

Decisions and what spoke against them

Encrypted data, key in the keychain

Personal data is stored encrypted on the Mac. The key lives in the macOS keychain, not in the project folder. That costs more effort and carries a risk: if the key is lost, the data is gone. I accept that risk.

An extra confirmation for sensitive tools

Tools that change something or touch personal things need an extra confirmation, on the Mac also via Touch ID. I have to consciously decide for every new tool whether it belongs behind this lock. Exactly this gap was found by one of my security reviews: a tool I had forgotten to classify.

Tests protect the real data

The tests run with redirected data paths so they never change my real data. How I learned that is in the note on tests.

Tests locally, cloud only at night

The repo is private, and GitHub’s free compute minutes are limited. In October they ran out once. Since then I test locally and push sparingly. In addition, a cloud run on Linux, the “night watch”, runs at night. It runs the tests and reports failures. That catches things that only work on my Mac. The downside: that run does not see Mac-specific tests.

Night-shift routine with draft PRs

I write an issue and give it a label. At night a routine takes the oldest of these issues, builds it on its own branch, runs the tests and opens a draft PR. It never merges. I do that myself in the morning. If there is no issue, it does nothing. More on this in the note on agents (German).

One codebase for Mac and Windows

I didn’t want to maintain a second version. That is why Mac code sits behind a platform layer, and Windows runs in CI. The price: everything that only works on the Mac has to be marked cleanly.

What I learned

  • For an assistant with tools, security mostly means: classify every new tool.
  • An assistant that is allowed to act needs confirmations in the code, not only in the prompt.
  • With AI agents I build faster. I still have to check things myself.

Limits

Some tests fail now and then, for example because of timing, network problems or high load. Some of the newer features have not yet been tried in everyday use. And over 4,400 tests only say that the cases I thought of work.

Why the code is private

Jarvis works with very personal data. Even clean code gives hints about what exists and where it lives. So I show the architecture, but no code and no screenshots with content. Public and ready to show instead is Agent-Board.
